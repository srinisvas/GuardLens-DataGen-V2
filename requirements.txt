# --- VERSION PINNING POLICY ---
#
# vLLM is pinned to an EXACT version (0.28.0) because it is the only
# component that both (a) requires the specific Qwen3.5 reasoning-parser
# and default_chat_template_kwargs machinery this benchmark depends on,
# and (b) has an aggressive dependency graph that will conflict with
# anything we pin manually. Let vLLM pull its matching torch, transformers,
# huggingface_hub, safetensors, protobuf, FlashInfer, etc. We do NOT
# redundantly pin those here.
#
# Runtime compatibility note for Python 3.11 / cluster nodes:
#   vLLM 0.28.0 resolves to a FlashInfer build whose comm/fd_exchange.py
#   contains array.array[int], which is not runtime-subscriptable on Python
#   3.11. runtime_compat_v12.py applies the exact upstream postponed-
#   annotations compatibility fix before model loading, in an idempotent and
#   GPFS-lock-protected way. The SLURM jobs also set
#   VLLM_USE_FLASHINFER_SAMPLER=0 so sampling uses vLLM's native path and does
#   not require an external nvcc/CUDA_HOME for FlashInfer JIT compilation.
#   VLLM_ALLREDUCE_USE_FLASHINFER=0 is explicitly locked as well.
#
# Non-vLLM dependencies are floor-pinned only. These are packages vLLM
# does not depend on, so there is no conflict risk.
#
# AFTER PHASE 1 PASSES with this file, capture the exact resolved
# versions with:
#     pip freeze > requirements.lock.txt
# and treat requirements.lock.txt plus runtime_compat_v12.py as the
# reproducible runtime artifact for the paper. Do not leave `>=` ranges in
# the frozen environment description.
#
# If Phase 1 preflight reveals a genuine vLLM/Qwen3.5 incompatibility after
# these environment fixes, switch to a pinned tested build rather than
# relaxing version constraints ad hoc.
